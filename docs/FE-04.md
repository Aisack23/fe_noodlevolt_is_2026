# FE-04 — Pedido para llevar: integración de creación

## Contrato integrado

La pantalla `/pedidos/llevar` usa `POST /orders` a través de una Server Action. El token de la cookie `httpOnly` se reenvía como `Authorization: Bearer`; nunca se expone al componente cliente.

El cuerpo respeta `CreateOrderDto`:

```json
{
  "branchId": "UUID",
  "operationKey": "UUID",
  "paymentMode": "ONLINE | AT_COUNTER",
  "lines": [{ "dishId": "UUID", "quantity": 1, "expectedPrice": "8.50" }]
}
```

`CAJA` es solo la etiqueta interna y visible del frontend; se adapta explícitamente a `AT_COUNTER`. La respuesta del servidor se valida y se adapta a la confirmación existente. Los totales y los precios de líneas se muestran desde la respuesta del servidor.

## Sucursal del menú

`/menu` consulta `GET /branches` público y elimina la dependencia de `MENU_BRANCH_ID`. La selección se refleja en `?sucursal=<uuid>` y al agregar platillos queda persistida con el carrito. Para evitar mezclar catálogos, la interfaz solicita vaciar un carrito con productos antes de cambiar a otra sucursal.

## Sesión y reintentos

Al pulsar confirmar, el cliente exige sesión y rol `CLIENT`. Sin sesión, redirige a `/login?returnTo=/pedidos/llevar`; tras un inicio de sesión correcto vuelve al carrito persistido. El servidor vuelve a comprobar token y rol antes de llamar a la API. Un 401 borra la cookie y reactiva ese retorno.

La `operationKey` se conserva en `sessionStorage` mientras no cambien sucursal, modalidad, platillos, cantidades ni precios esperados. Esto permite reintentos seguros tras un error de red y se elimina solo después de un 200/201 exitoso. El carrito se limpia únicamente en ese punto.

## Errores

Los 400, 403, 404 y 409 se presentan como mensajes de usuario; para 409 se conserva el motivo concreto del backend, por ejemplo sucursal cerrada, platillo no disponible, cambio de precio o clave de operación reutilizada. Un 401 conduce a inicio de sesión. La solicitud permanece reintentable y el carrito no se modifica en ningún error.

## Limitación detectada en backend local

Al inspeccionar `be_noodlevolt_is_2026/src/orders/repositories/orders.repository.ts`, la creación asigna `paymentMode: 'ONLINE'` y no asigna `pickupAt`, aunque el DTO acepta `AT_COUNTER` y la documentación promete ambos valores. El frontend envía el contrato correcto y muestra la respuesta real; si `pickupAt` llega `null`, la confirmación muestra **Por confirmar**. Esta discrepancia debe corregirse en backend antes de aceptar pruebas completas de modalidad y hora.
