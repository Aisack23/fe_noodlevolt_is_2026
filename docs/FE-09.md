# FE-09 — Campana y buzón de notificaciones

## Rutas y acceso

| Ruta | Uso | Acceso de interfaz |
|---|---|---|
| `/notificaciones` | Buzón del cliente (página completa) | Sesión requerida |
| Campana del navbar | Panel desplegable con los mismos avisos | Visible con sesión |

Las comprobaciones por rol son apoyo visual. La API mantiene la autorización definitiva (401 sin sesión, 403 para personal). El token vive en una cookie `httpOnly`; el navegador nunca lo lee.

## Contrato integrado

`GET /api/v1/notifications/me?page=1&limit=20` (BE-09) devuelve:

```json
{ "items": [{ "id", "type", "title", "message", "orderId", "isRead", "createdAt" }], "total": 1, "page": 1, "limit": 20 }
```

Flujo: navegador → `GET /api/notifications` (route handler en `app/api/notifications/route.ts`, lee la cookie) → backend. Un buzón vacío responde 200 con `items=[]`, no 404. Solo se pide la primera página (20 avisos).

## Archivos

- `lib/api/notifications.ts` y `lib/api/notifications-client.ts`: tipos y llamadas (servidor y navegador).
- `lib/hooks/useNotifications.ts`: consulta y sondeo cada 15 s, solo con el panel abierto y la pestaña visible. Se detiene ante 401/403. La primera carga se difiere con `setTimeout` para cumplir la regla `react-hooks/set-state-in-effect`.
- `lib/format-relative-time.ts`: «ahora», «hace 2 min», «ayer».
- `components/business/NotificacionesContenido.tsx`: estados carga, vacío, error, sesión no válida y lista.
- `components/ui/Campana.tsx`: botón y panel (400 px). `NavbarCliente.tsx`: se agregó `relative` al grupo de acciones para anclar el panel al borde derecho.
- `app/notificaciones/`: página, `error.tsx` y `loading.tsx`.

- Sin contador en la campana, sin «N sin leer» y sin resaltado crema: BE-09 no expone endpoint para marcar como leído y el GET no cambia `isRead`, así que el contador nunca bajaría. `isRead` ya viene en el tipo para reactivarlo.
